# 用户需求：文件级权限管理（File-Level Permission Management）

> 需求来源：wiki 页面 [04 账户体系&资源体系 记录](https://wiki.sangfor.com/pages/viewpage.action?pageId=274119996)（v11）
> 状态：待转换系统需求

## 1. 背景与问题

当前 FastGPT 的权限体系以 **team 为资源绑定单位**，权限粒度仅到资源类型（dataset / app / evaluation / model 等），通过 `resource_permissions` 表管理，verb 为 read / write / manage。

现有痛点：**权限粒度不足**。同一个知识库（dataset）下的不同文件（collection / 文档），无法区分「谁能看、谁能改、谁不能看」。

```
需求来源原文：同一个文件，有些人能看，有些人能改，有些人不能查看
```

**重要边界**：知识库检索（KB 检索 / RAG 检索）的召回需**按文件级权限过滤**（见 US-11），用户仅能召回有查看权限的 collection 内容；本次在扩展资源管理权限能力的同时，将检索链路的权限判定下沉到文件级。

## 2. 用户角色

| 角色 | 说明 |
|------|------|
| 团队拥有者（team owner） | 拥有团队内所有资源的 owner 权限，可转移所有权 |
| 资源拥有者（resource owner） | 拥有某个 dataset / collection 的所有权 |
| 协作者（collaborator） | 通过 tmbId / groupId / orgId 被授予 read / write / manage 权限 |
| 团队普通成员 | 通过 team / org / group 层级继承权限 |

## 3. 用户故事

### US-1 文件级查看权限
作为知识库管理员，我希望**同一个文件**（collection）可以被配置为「某些人可看、某些人可改、某些人完全不可见」，以便按文件控制团队成员的访问范围。

### US-2 文件夹权限生效范围
作为知识库管理员，当我给一个文件夹（folder 类型 collection / dataset）配置权限时，我希望可以设置**生效范围**：
- **对所有子集资源生效**（默认）：权限下发给所有子资源；
- **仅对当前资源生效**：权限只作用于当前资源本身，子资源不继承；
以便灵活控制权限的传播范围。

### US-3 默认继承父级权限
作为知识库管理员，我默认希望子资源自动继承父级权限（生效范围=对所有子集生效时），子资源不需要重复配置。

### US-4 仅当前生效时不继承
作为知识库管理员，当我将某个资源设置为「仅对当前资源生效」时，我希望所有子资源停止继承、转为独立权限状态，避免子资源意外获得权限。

### US-5 移动文件时的权限处理
作为知识库管理员，当我把一个文件/文件夹移动到另一个目录时，我希望可以选择：
- **继承新父目录的权限**（默认）：移动后资源权限与新父目录一致，且不残留旧权限；
- **保持独立配置**：移动后保留原有独立权限；
以便移动文件时权限不泄漏、不残留。

### US-6 恢复继承
作为知识库管理员，当我把一个独立配置的资源「恢复继承」时，我希望：
- 资源权限干净地回到父级权限（清除自身除所有者外的配置）；
- 若为文件夹，其所有继承态子资源同步恢复；
以便把误配置的权限一键还原。

### US-7 文件级协作者配置
作为知识库管理员，我希望可以为**单个文件（collection）**直接配置协作者（而不只是 dataset 级别），以便对特定文件单独授权。

### US-8 冲突时取消继承
作为知识库管理员，当我配置的资源权限与父级**冲突**（例如子级权限比父级小）时，我希望系统自动将该资源切换为非继承态，并保留独立配置；若权限变大则无需冲突、继续继承。

### US-9 所有权转移
作为团队拥有者 / 资源拥有者，我希望可以将 dataset 或 collection 的所有权转移给其他成员，且转移后新旧所有者权限冲突能正确处理。

### US-10 一键升级/重新配置
作为系统管理员，我希望在权限继承逻辑升级后，可以**从根开始按新逻辑重新配置所有权限**，以便存量数据自动迁移到新规则。

### US-11 知识库检索按文件级权限过滤
作为知识库使用者，我希望知识库检索（RAG 检索）的召回结果**按文件级权限过滤**：我只能检索到有查看权限的文件（collection）中的内容，没有权限的文件内容不会被召回；以便检索结果与文件级权限保持一致，防止越权检索。


## 4. 业务规则（约束）

- 权限位定义：read = 0b100（4）、write = 0b010（2）、manage = 0b001（1）；owner = 32 位全 1。
- 生效范围字段：`allChildren`（对所有子集资源生效，默认）/ `currentOnly`（仅对当前资源生效）。适用对象：dataset（所有）、collection（folder 类型）。
- 继承态资源：非 folder 资源无任何独立 clbs 配置（仅保留所有者）；folder 资源的 clbs 与父级完全一致。
- 资源操作权限门槛：
  - 创建 collection：需 dataset write 及以上；
  - 修改 collection：需 collection write 及以上；move 操作需 source 与 dest folder 的 manage 权限；
  - 查看 / 列表 collection：需 collection read 及以上；
  - 删除：dataset / app 需 owner 权限，collection 需 write 权限；
  - 转移所有权（changeOwner）：需 owner 权限。
- 子资源定义：
  - dataset 的子资源：`type=folder` 且 `parentId=当前id` 的 dataset；以及所有 collection；
  - collection 的子资源：`type=folder` 且 `parentId=当前id` 的 collection。
- 权限校验输入：resourceId、tmbId；校验顺序为「继承态取父级权限 → 自身权限 → 叠加 group / org」。

## 5. 范围

### 范围内
- collection 级别的权限配置（协作者、生效范围、继承/独立状态）
- dataset / collection 文件夹的权限传播与继承逻辑
- 移动（move）、恢复继承、所有权转移、权限冲突检测
- 存量权限按新逻辑的一键升级
- **知识库检索（RAG 检索）的召回按文件级权限过滤**（用户仅能检索到有查看权限的 collection 内容）

### 范围外
- 团队 / 组织 / 用户组本身的管理
- 非 KB 资源（evaluation / model 等）的行为调整

## 6. 关键非功能关注点

- **性能**：上千/上万个文件的列表权限过滤不能有明显的性能退化；权限递归深度（如 10 层 dataset + 10 层 collection）需可控。
- **检索性能**：检索（RAG 召回）为高频热路径，文件级权限过滤不得造成明显的检索延迟退化；需评估并约束召回链路中权限过滤的额外开销。
- **检索正确性**：用户仅能召回有文件级读权限的 collection 内容；不得因文件级过滤导致越权召回或漏召回。
- **正确性**：移动 / 恢复继承 / 配置变更后权限无残留、无冲突、无泄漏。
- **兼容性**：存量数据在升级后权限语义正确迁移。
